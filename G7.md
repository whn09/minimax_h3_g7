# MiniMax-H3 on one g7.48xlarge (8× RTX PRO 4500, 32 GB): what is fast, and what is not available

The question was **"在保证质量的情况下怎么最快"** on g7.48xlarge — eight RTX PRO 4500 Blackwell cards,
31.37 GiB usable each, PCIe only, no NVLink, `sm_120`. Everything below is measured on this box with
one prompt, one seed (42), one length (768p, 121 frames = 5.04 s), driven by
[`scripts/g7_sweep.sh`](scripts/g7_sweep.sh).

**The short answer.**

| you want | run | 5 s clip |
|---|---|---|
| t2va, exact math | fp8, `--tp-size 4 --ulysses-degree 2` | **105 s** (4.21 s/step × 25) |
| ref2va, exact math | fp8, `--tp-size 4 --ulysses-degree 2` | **174 s** (6.98 s/step × 25) |
| **t2va, recommended** | bf16 + lightx2v 8-step **fl2v** LoRA + `--minimax-h3-adaln-online` + `--text-encoder-cpu-offload true`, TP=4×U=2 | **39 s** (4.93 s/step × 8) |
| **ref2va, recommended** | the same with the 8-step **ref2v** LoRA | **63 s** (7.91 s/step × 8) |

So the exact-math floor is **1.7 min (t2va) / 2.9 min (ref2va)** per 5-second clip, and the distill
LoRA takes it to **0.7 min / 1.1 min**. Multiply by ~2 for a 10 s clip (241 f) and ~2.9 for 15 s
(345 f).

**One thing that sounds like a lever and is not:** TP=2 × Ulysses=4 cannot beat TP=4, and mostly
cannot even load — §3.1. **And one that half is:** Cache-DiT's *audited* switch (`quality="high"`) is
refused on this hardware and `--cache-dit-config` is a diffusers-only flag, but the
`SGLANG_CACHE_DIT_*` env / per-request route is open and unaudited — §4.

**And one lever this document previously said did not exist: SageAttention.** It is not gated on
sm_120 the way FlashAttention and VSA are, it was already in the image, and installing it is worth
**1.23× on t2va (105.92 → 85.85 s) and 1.32× on ref2va (177.18 → 134.29 s)** at slightly *lower*
peak memory, with only the backend changed. It is an approximation, so it needs a quality gate. See
**§2.1**, which corrects §2. Credit for the lead: the `minimax_h3_g7e` work on RTX PRO 6000
(sm_120, 96 GB), which had already established sage, NVFP4 and FA4-is-closed on this architecture.

**And the thing that actually mattered more than any of this:** the two renders the customer rejected
were rejected for prompt-layer reasons, not speed — see [`PROMPT_IR.md`](PROMPT_IR.md). Doubling the
step count fixed nothing and cost 108 s; rewriting the prompt fixed both cases and cost 0.55 s.

## 2. What is simply not available on this card, and why

This is half the value of the sweep: it closes questions rather than answering them.

**No FlashAttention. At all.**

```
runtime/platforms/cuda.py:513  _FlashAttentionBackendResolver.resolve()
    if platform.is_sm120():  -> TORCH_SDPA
runtime/platforms/cuda.py:696  "Defaulting to Torch SDPA backend on SM12.x"
```

FA3/FA4 are hard-gated off for `sm_120` regardless of what `--attention-backend` asks for, which is
why `fa` and `cudnn` are *measured no-ops* — 105.68 / 104.35 / 105.37 s is the same number three
times. FA2 is not gated, it just does not exist in the image:

```
sglang/.../attention/flash_attn_2.py:13
    ImportError: cannot import name 'flash_attn_func' from ...flash_attn
```

**No sparse attention.**

```
ValueError: VSA-H3 (video_sparse_attn_h3) needs compute capability 9.0 (Hopper),
10.0 (B200 / GB200) or 10.3 (B300 / GB300); this device reports 12.0.
```

VSA was the single largest lever on paper (sparsity 0.9 at 25 steps). It cannot run here.

**So `torch_sdpa` is the only *dense, exact* attention backend on g7.** The stronger claim this
section used to make — "there is no attention speedup to be had" — was **wrong, and wrong by
reasoning from the FlashAttention gate to a conclusion about attention in general.** SageAttention
is a different resolver with no `sm_120` gate at all, it was in the image the whole time, and it is
worth **1.23× (t2va) / 1.32× (ref2va)**. See §2.1.

### 2.1 SageAttention 2 **does** run on sm_120, and it is the only attention lever that does

`--attention-backend sage_attn` clears both gates that close everything else:

```
platforms/cuda.py  _SageAttentionBackendResolver.resolve()
    try: from sageattention import sageattn   -> ImportError: return AttentionBackendEnum.FA
    if platform.is_hopper():  <SM90 binding check>   # skipped entirely on sm_120
    return "...backends.sage_attn.SageAttentionBackend"
backends/sage_attn.py:83   SageAttentionImpl.forward_varlen()   # overridden
```

The second line is the one that matters: H3's DiT runs **packed varlen** (video and audio tokens
concatenated into one ragged sequence), so `minimax_h3.py:308` demands
`AttentionRequirements(packed_varlen=True)` and `minimax_h3.py:226 validate_server_args` raises
`ValueError` for any backend that does not override `forward_varlen`. That single test is what
refuses `sage_attn_3`, `video_sparse_attn`, `vmoba`, `block_sparse_attn`, `sliding_tile_attn` and
about nine others. `sage_attn` passes it. So does `sol_attn`; `subblock_sparse_attn` passes it but
needs `sm_100a`.

Measured, 768p / 121 f / seed 42 / 25 steps / fp8 / TP=4 × U=2 / `case_ir.txt`, i.e. **only the
backend moved** — the baselines are the already-recorded arms and neither was re-run:

| arm | `torch_sdpa` | `sage_attn` | | peak/card |
|---|---:|---:|---:|---:|
| t2va (1036-char IR prompt) | 105.92 s (4.24 s/step) | **85.85 s** (3.43) | **1.23×** | 27 088 MB |
| ref2va (3337-char IR prompt) | 177.18 s (7.09 s/step) | **134.29 s** (5.37) | **1.32×** | 27 692 MB |

Peak memory goes slightly **down**, so this costs nothing in the dimension that constrains this card.
Sage is an approximation (int8 QK with a smoothed mean, fp8 PV), so it belongs in the approximate
table and needs the same quality gate as the distill LoRA.

**It must be built from source, in the container that serves.** `pip install sageattention` gets
1.0.6, a pure-Triton build worth only ~1.16×; the source build at `d1a57a5` is what these numbers
are. `TORCH_CUDA_ARCH_LIST=12.0`, ~4 min at `MAX_JOBS=32`, and it lands in that container's
site-packages only — delete the pod and `--attention-backend sage_attn` silently stops being sage.
Run the import check from **outside** `/sgl-workspace/SageAttention`, or you hit the compiled
extension shadowing (`cannot import name '_fused'`) and read a successful build as a failure.

**The failure mode is silent and reads as a clean negative.** If `sageattention` is missing the
resolver returns `FA`, and `FA` on sm_120 is itself downgraded to `TORCH_SDPA` — so "sage did
nothing" and "sage was never installed" both produce 105 s, which is precisely the number the arm is
being compared against. `scripts/sage.sh` therefore reads the backend back out of the serve log
(`Using sage_attn attention backend`) and **skips the render** if it is not sage, rather than
spending 175 s to reproduce a baseline. Exempt the components that cannot take it —
`--component-attention-backends text_encoder=torch_sdpa,audio_vae=torch_sdpa,video_vae=torch_sdpa`
— because Qwen3VL's `LocalAttention` accepts only `{fa, torch_sdpa}` and on newer sglang an explicit
global `--attention-backend` stops falling back and hard-fails the server instead
(sgl-project/sglang#35743).

Everything left after this is topology, weights and step count.

**`--cache-dit-config` is silently ignored on H3.** It is consumed at
`runtime/pipelines/diffusers_pipeline.py:592`; H3 runs the *native* pipeline. Measured: byte-identical
mp4 and 105.40 s against 105.37 s, and its own help text says "for diffusers backend". The real
switches are the `SGLANG_CACHE_DIT_*` env vars and the per-request `enable_cache_dit` /
`cache_dit_params` / `quality` fields — see §4.

**`--enable-torch-compile` is a 24 % loss** (130.53 s vs 105.37 s). Inductor's GEMM autotuner also
prints `torch.OutOfMemoryError: out of resource: triton_mm Required: 131072 Hardware limit: 101376`
as *normal operation* while it rejects candidates — that 99 KB is this card's shared memory per block
against an H100's 227 KB, and it is the same reason several hand-written kernels have no `sm_120`
build. A readiness watcher that treats `Traceback` or `out of memory` as fatal throws this arm away;
`up()` in the sweep script matches only the two messages that actually end startup, plus the server
process disappearing.

**No NVLink**, so `CustomAllReduce is disabled ... more than two PCIe-only GPUs`. Collectives go over
PCIe + 2× EFA, which is why the topology optimum is not the H100's.

## 3. Why TP=4 × Ulysses=2, and why 32 GB decides it

`GPUS = TP × ULYSSES` is the only constraint, so the sweep is a search over factorisations of 8.

* **TP=8 × U=1 is 35 % slower** (5.71 vs 4.21 s/step). Eight-way per-layer all-reduce over PCIe.
* **TP=2 × U=4 would be the fastest shape and cannot load.** `--quantization fp8` is **online**
  quantization: the loader lands the bf16 checkpoint on the card and casts after, so `65.65 GiB / TP`
  must fit in 31.37 GiB. That is a hard **TP ≥ 4** floor on this card, and TP=2 dies with
  `29.65 GiB is allocated` during transformer load.
* **`--minimax-h3-adaln-online` is the flag that would have lifted the floor, and it is bf16-only.**
  Of the 61.73 GiB DiT, `adaln`-named tensors are **24.29 GiB — 39 % of the checkpoint**. Taking them
  off the card leaves 18.7 GiB to load at TP=2. But:
  `ValueError: MiniMax H3 AdaLN cache is only compatible with unquantized weights`, so `adaln_tp2`
  and `adaln_tp4` both fail on fp8. The flag is only usable on the bf16 + LoRA path, where it is
  exactly what makes that path fit (§5).

So on a 32 GB card the fp8 optimum is pinned at TP=4 × U=2 by the loader, not by the collectives.

### 3.1 "TP=2 × U=4, or even TP=1 × U=8, might be faster" — measured, and no

Right instinct, wrong hardware. `num_attention_heads = 56`
(`FL2VA/transformer/config.json`), so 2, 4 and 8 all divide the heads — **Ulysses degree is never the
blocker; memory is.** Three arms, all bf16 because that is the only precision `--minimax-h3-adaln-online`
accepts and that flag is what makes TP=2 conceivable at all:

| arm | weights/card | what happened |
|---|---:|---|
| bf16 TP=2 × U=4, text-encoder offload only | 18.7 GiB | OOM **loading the video VAE** at 30.59 GiB allocated — 1–2 GiB short |
| bf16 TP=2 × U=4, + `--image-encoder-cpu-offload` + `--vae-cpu-offload` | 18.7 GiB | weights and VAE now fit; OOM in the **warmup forward** at 30.52 GiB |
| bf16 TP=1 × U=8, same offloads | 37.4 GiB | OOM in the **transformer load** at 30.44 GiB — arithmetic, not a surprise |

The interesting one is the middle row: at TP=2 the weights *do* fit (18.7 GiB of DiT, plus a 2.31 GiB
on-GPU AdaLN rebuild slab — `MiniMax H3 AdaLN rebuild slab: 64 plans x 4 timesteps = 2.31 GiB`), and it
is the ~11 GiB of activations that does not. There is no flag for that: `--dit-layerwise-offload` moves
*weights*, and the weights were never the problem at TP=2.

**And it would not have won even if it fit**, which is the part worth keeping. The control arm says
what bf16 costs at the known-good topology:

| | s/step |
|---|---:|
| fp8 TP=4 × U=2 | **4.21** |
| bf16 TP=4 × U=2 (adaln-online + all three offloads) | **5.04** — **+19.7 %** |
| fp8 TP=8 × U=1 | 5.71 |

Halving TP from 8 to 4 bought 26 % (5.71 → 4.21); halving again to 2 is worth less than that on a
diminishing curve, call it 10–15 %. So bf16 at TP=2 lands around 4.3–4.5 s/step — **at best a wash
against fp8 at TP=4, and probably worse.** The topology gain does not cover the precision penalty.

**The only configuration that would actually win is a pre-quantized checkpoint**, and that is the real
takeaway from §3.2 below: fp8 *offline* at TP=2 would be 15.5 GiB of weights per card **and** keep
fp8's 4.21 s/step, which is where the win is. `--transformer-weights-path` exists for exactly that
("Path to pre-quantized transformer weights … Used by Nunchaku (SVDQuant) and quantized single-file
checkpoints"). Nobody publishes one for H3, so it is a project, not a flag.

### 3.2 NVFP4: the card supports it, the software needs a checkpoint nobody ships

RTX PRO 4500 Blackwell is `sm_120` with 5th-gen tensor cores, so FP4 is real silicon here, and
SGLang knows it — there is an sm_120 NVFP4 GEMM in the tree
(`sglang/kernels/kda_kernels/qwen3x_nvfp4_gemm_sm120.py`) and the Nunchaku path explicitly whitelists
this generation: *"Nunchaku SVDQuant is currently only supported on Ampere (SM8x) or SM12x GPUs"*
(`multimodal_gen/configs/quantization/nunchaku.py:124`). The blocker is upstream of the kernels:

* **`--quantization` does online quantization for `fp8` and `mxfp4` only** — the help text is explicit,
  and `mxfp4` targets ROCm MI350+ (gfx95x), not CUDA. Everything else
  (`modelopt`, `modelopt_fp8`, **`modelopt_fp4`**, `mxfp8`, `mxfp4_npu`, `modelslim`) **requires a
  pre-quantized checkpoint.**
* **`--enable-svdquant` requires `--transformer-weights-path`** (`nunchaku.py:131`), and infers
  precision from a filename matching `svdq-(int4|fp4)_r(\d+)`.
* **`MiniMaxAI/MiniMax-H3` publishes 280 files and not one of them is fp8, fp4, int4 or svdq.** It is
  a bf16-only release, and Nunchaku ships SVDQuant checkpoints for FLUX / Qwen-Image / Wan, not H3.

So NVFP4 on this box is not a flag we failed to find — it is a checkpoint that does not exist. Making
one is a bounded project (TensorRT Model Optimizer calibration + export for `modelopt_fp4`, or a
Nunchaku SVDQuant conversion with the low-rank branch), and it is the **only** thing that would move
the topology floor: at 4 bits the DiT is ~15.4 GiB, which fits TP=2 comfortably and fits **TP=1 × U=8**
for the first time. If g7-class hardware is the long-term target, that conversion is the highest-value
engineering item on this list. Until then TP=4 × U=2 is the floor, and the step count (§5) is the lever.

**Update: that project has already been done, on the sibling card, and it works.** The
`minimax_h3_g7e` work quantizes both partitions from stock bf16 itself
(`nvfp4_quantize_transformer.py`, ~10 min of pure CPU each: 208 linear layers to nvfp4 + 50
`adaln_proj.linear.weight` to bare fp8 + the rest bf16 = 951 tensors, round-trip relative error
0.094 ± 0.002, which is the group-16 e2m1 quantization floor) and loads it with
`--transformer-weights-path`. Four things to carry over verbatim, because each was a bug they hit:

* **Do not pass `--quantization modelopt_fp4`.** The config inferred from the safetensors is the
  correct one; naming it explicitly builds an empty, unusable config.
* **Two source patches are mandatory** and both fail *silently* into a grey smear rather than an
  error: the sm_120 FP4 GEMM scale layout (on this arch `backend="auto"` enters neither branch, so
  per-layer relative error is 0.55 instead of 0.095) and the `qkv_proj` per-row block scales, whose
  rows the DiT loader permutes without permuting the scales (52 layers get the wrong scale).
  Upstreamed as sgl-project/sglang#35739 and #35740 — both **newer than our image**, which is
  `20518d85`. Their retirement test is byte-identical output with the patches skipped.
* **NVFP4 alone is a *regression* at 768p** — 15–17 % *slower* than fp8+sage — because weight
  quantization never touches attention and **attention is 59 % of a 768p step**. It only wins paired
  with sage (then 32/32 cells). So §2.1 is the load-bearing half of this recipe and NVFP4 is the
  second-order one. Do not do NVFP4 first.
* **Their peak is 52.0 GB per card at TP=1, on a 96 GB card.** That is the whole difficulty of
  porting it here: 31.37 GiB forces TP ≥ 2, and **they never used tensor parallel at all** — every
  arm is `GPUS=1 ULYSSES=1` or `GPUS=2 ULYSSES=2`. So NVFP4 × TP is an unvalidated combination, and
  the specific thing to distrust is the qkv scale-reorder patch: it runs in
  `process_weights_after_loading`, where a TP rank sees only its own shard, and getting it wrong
  produces a picture rather than an exception. First render must be inspected by eye.

The prize is still what this section said it was, and it is bigger than the 1.26× they measure: 24.4 GB
of NVFP4 weights is **12.2 GB per card at TP=2**, which is exactly the shape §3.1 called "the fastest
shape and it cannot load". It could not load only because `--quantization fp8` is *online* and needs
the bf16 checkpoint to land on the card first. A pre-quantized file removes that constraint entirely.

### 3.2.1 Ported, run, and it renders **noise**. Timings below are not usable numbers.

Both partitions were converted here and both arms served and completed. **The output is pure
per-latent-cell colour noise — not a soft picture, not a grey smear, noise** (`out/*nvfp4*.mp4`,
frame 60). So the two timings are the cost of computing garbage and neither belongs in a
recommendation:

| arm | inference | s/step | vs sage | peak/card | verdict |
|---|---:|---:|---:|---:|---|
| t2va@wide NVFP4+sage | 78.45 s | 3.14 | 1.09× | 27 178 MB | noise |
| ref2va NVFP4+sage+enc-offload | 125.33 s | 5.01 | 1.07× | **20 968 MB** | noise |

The bitrate is the cheapest tell and it is unambiguous: at identical geometry (1344×768, 124 f) the
sage renders encode to **0.86–0.99 Mbps** and both NVFP4 renders to **12.45–12.51 Mbps**. Two
independent arms landing within 0.5 % of each other at 12.5× the entropy is noise, not a variation.

**What was ruled out, so the next attempt does not redo it.** Neither g7e patch is needed or wanted
on this image, and both facts were read out of the source rather than assumed:

* `patch_nvfp4_tma_scale_layout.py` (#35739) **has landed, generalised**. The condition it widened is
  gone: `modelopt_quant.py` early-returns for `trtllm` and then applies the 128×4 TMA
  reshape/permute unconditionally, commented "Every FP4 GEMM reachable here reads block scales in the
  128×4 TMA layout". `H3_FP4_TMA_SCALES` is a dead env var here.
* `patch_h3_qkv_scale_reorder.py` (#35740) **has landed, generalised, and applying the patch on top
  would break it.** Upstream iterates `self.qkv_proj.named_parameters()` and reorders every
  row-indexed sibling of the permuted weight, gating on row count and handling
  `BlockQuantScaleParameter` by scaling both the permutation and the gate by the block height — where
  the patch knew only the two names `weight_scale`/`weight_scale_inv`. A second reorder is exactly as
  wrong as none, and just as silent. This was also read as answering the TP-rank worry, because the
  scale reorder installs `rank_local_weight_transform`. **It only half answers it** — the reorder is
  TP-safe, but the *shard extraction* it feeds is not the one bf16 uses. See §3.2.2.

What is *not* wrong: the file and the config agree. The server reports `Detected nvfp4 checkpoint` and
builds `group_size=16, 268 excluded modules, packed_qkv=False, comfy_quant=False, scale_layout=linear,
swap_nibbles=False` — exactly what our quantizer writes — and the weight round-trip error is on the
0.095 group-16 floor.

This section first named the **activation** side as the surviving suspect, on the grounds that the
checkpoint carries no `input_scale`. **That is withdrawn**: §3.2.2 traces it to
`missing_param_init="ones"`, which #35740 changed `_mark_missing_params_required` specifically in order
to preserve, so the absent `input_scale` is a declared and handled case rather than a hole. §3.2.2 has
the real analysis, the one axis that differs from a known-working configuration, and the bisection.

**Two findings from the port that are true regardless, and both are about memory, not speed.**

* **The 50 `adaln_proj.linear` weights must be resident fp32** whenever curve AdaLN is on —
  `minimax_h3.py:2081` raises `"must stay fp32 with curve AdaLN"` — no matter what dtype the
  checkpoint stores. They are 40 % of the DiT's weights, so **fp32 AdaLN is the memory floor under
  every arm on this card, quantized or not.** That is why NVFP4 did not buy the topology freedom §3.2
  promised: quantizing the other 60 % cannot get under a floor set by the 40 %. ref2va OOMed during
  *load* at 30.59 of 31.37 GiB, with the **video VAE** failing to find its last 64 MB, and needed
  `--layerwise-offload-components text_encoder` to fit.
* **g7e's fp8-AdaLN half of the recipe does not load on this image at all**, and it fails loudly in
  two independent places rather than rendering something wrong: `quantization_utils.py:160` treats any
  `F8_E4M3`/`I8`/`U8` `.weight` as quantized and demands a `comfy_quant` marker, so the undeclared
  adaln casts abort with *"Quantized weights are missing comfy_quant metadata"*; and declaring them
  `float8_e4m3fn` fails twice over — `:206` *requires* a `weight_scale` tensor that a bare cast does
  not have, and `:409` accepts only `["nvfp4"]` or `["int8_tensorwise","nvfp4"]` as a format **set**,
  so a float8+nvfp4 mix raises `"Unsupported Comfy quantization format(s)"`. `scripts/quant.sh`
  therefore keeps AdaLN in bf16 (free — 0 % of the FLOPs) and the file is 37.5 GB, not 24.4 GB.

### 3.2.2 Why it renders noise here and not on g7e: **g7e never runs tensor parallelism**

Re-read of the `minimax_h3_g7e` project against this image's actual source (`sglang` at `20518d85`,
fetched per-file at that exact ref rather than inferred). Every other axis of their recipe matches
what we ran; **the one axis that does not is TP, and their README never mentions it once** — grep for
`tp-size`, `tp_size`, `TP=` or `张量并行` across all 72 KB of it returns nothing. Their multi-card
arms are `GPUS=2 ULYSSES=2`, i.e. Ulysses only, TP=1 throughout, one full 62 GiB DiT per 96 GB card.

| | g7e (works, delivered) | us (noise) |
|---|---|---|
| weights | self-quantized NVFP4, same script | same script, byte-identical recipe |
| **TP** | **1, always** | **4 (forced — §3.1)** |
| Ulysses | 1 or 2 | 2 |
| sage exemptions | `text_encoder`, `audio_vae`, `video_vae` | same three |
| `SGLANG_USE_RUNAI_MODEL_STREAMER=0` | yes | yes |
| `SGLANG_DIFFUSION_FLASHINFER_FP4_GEMM_BACKEND=auto` | yes | yes |
| `H3_FP4_TMA_SCALES` / `H3_FP4_QKV_FIX` | `1` / `0`, **paired with the two patches** | unset, **patches retired** |
| AdaLN in the file | bare fp8 | bf16 (this image refuses fp8 — §3.2.1) |

The env-var row is not a discrepancy, and this is worth stating because it looks like one. Those two
env vars only exist to arbitrate against g7e's two source patches — *"NVFP4 的 qkv 行序修复只能有一处
生效 … 两个一起开就是 reorder 两次，和一次都不做一样坏"*. Both patches are now upstream (#35739,
#35740), and g7e verified the retirement criterion empirically: `FP4_UPSTREAM=1` (no patches, none of
the three FP4 env vars) rendered **md5 bit-identical** output to the patched path. So "no patches, no
env" is the *correct* configuration on this image, which the source confirms at our exact commit —
`_install_qkv_row_reorder` is present at `minimax_h3.py:262`, and the 128×4 TMA reshape at `:783` is
unconditional with the comment *"Every FP4 GEMM reachable here reads block scales in the 128x4 TMA
layout"*.

**What TP>1 changes in the load path, and it is not nothing.** `minimax_h3.py:319
_copy_grouped_qkv_tp_shard` is the function that extracts a rank's own Q/K/V rows from the fused,
head-interleaved checkpoint tensor. It **refuses a packed 4-bit weight twice over**:

```python
or getattr(param, "packed_dim", None) is not None        # NVFP4 packs K into uint8 -> refused
or param.dtype not in (_BF16_DTYPE, torch.float8_e4m3fn)  # NVFP4 weight is uint8 -> refused
```

So bf16 and **online fp8 take the TP-aware fast path; NVFP4 cannot**, and falls back to
`base_loader(param, _reorder_checkpoint_weight(loaded_weight))`. On paper that fallback is still
correct — `qkv_proj` is a `MergedColumnParallelLinear` (`:787`, whose own comment says *"a plain
ColumnParallelLinear would instead slice across the concatenated tensor and is incorrect for TP > 1"*),
its loader splits a fused tensor into three shards itself, and `_install_qkv_row_reorder` gates on the
**full** checkpoint row count so it survives sharding. Also checked and cleared: our config is
`packed_qkv=False, comfy_quant=False, scale_layout=linear, swap_nibbles=False`, which matches what our
quantizer writes; `checkpoint_uses_native_qkv_layout` defaults `False` (`base_config.py:38`) so the row
reorder *is* installed; the missing `input_scale` is legitimately synthesized — `mg/modelopt_quant.py:671`
sets `missing_param_init="ones"` and #35740 changed `_mark_missing_params_required` specifically to
preserve that, so **the activation scale is not the bug** and that earlier suspect is withdrawn.

Which is the whole point: this failure mode is silent, so paper review has now run out of leads, and
the remaining difference from a working configuration is a single axis nobody has ever exercised.

**The cheap bisection, if this is ever picked up again** — ranked by information per GPU-minute, and
none of it is worth doing for a 7–9 % gain on top of sage:

1. **Quantize everything except `qkv_proj`** (156 layers instead of 208; one `QUANT_RE` edit, ~2 min
   CPU per partition). Clean render ⇒ the defect is the qkv row/scale path under TP, which is a third
   upstream PR. Still noise ⇒ it is the FP4 GEMM or the row-parallel `out_proj` shard, not the reorder.
2. **Run NVFP4 at TP=1 with `--dit-layerwise-offload`.** It will be far slower than any number in this
   document, and that does not matter: it is the only way to reach TP=1 on a 32 GB card, and a clean
   render there converts "TP is the suspect" into "TP is the cause" in one arm.
3. **`--minimax-h3-adaln-online` + TP=2 × U=4** — worth running only after 1 or 2 says the low-TP
   path is sound, and **not for the reason first written here.** The flag does not remove the curve
   grid: `adaln_curve_grid` is set from the checkpoint's own `time_table_size`
   (`configs/models/dits/minimax_h3.py:146`), not by any flag, so `:1254`'s fp32 choice stands. What
   the flag does is stop *precomputing and holding* the AdaLN plan cache — it **streams** the native
   `blocks.N.adaln_proj.linear.weight` tensors and rebuilds plans per timestep, which is why it
   measures 18.7 GB/card at TP=2 instead of ~26. It is also why the flag is **bf16-only**: the
   rebuild source has to be a checkpoint carrying those native tensor names, and
   `minimax_h3_adaln_cache.py` says so outright — "a checkpoint without them (Diffusers layout,
   quantized export) cannot serve as a rebuild source". An NVFP4 export is exactly such a
   checkpoint, so **this item cannot be run against an NVFP4 file at all** unless the adaln tensors
   are left in native bf16 by name, which is what `quant.sh` already does. Check that before
   spending the arm.

### 3.3 Where the time actually goes, per stage

Measured, 768p / 121 f / 25 steps, sage arms (`[StageName] finished in` lines in the serve log):

| stage | t2va | ref2va | parallelism |
|---|---:|---:|---|
| text encoding (Qwen3-VL) | 0.069 s | 1.650 s | replicated across all 8 ranks |
| visual encoding (reference image) | — | 0.556 s | replicated across all 8 ranks |
| latent + timestep prep | 0.020 s | 0.011 s | — |
| **DiT denoising** | **80.385 s** | **125.465 s** | **TP=4 × Ulysses=2 over 8 GPUs** |
| video VAE decode | 3.196 s | 3.238 s | replicated; not sharded |
| **total** | 83.67 s | 130.92 s | |

**The DiT is 96.1 % of a t2va request and 95.8 % of a ref2va one.** Everything else together is under
4 s and does not move with the accelerators, so every lever that matters is a DiT lever — which is the
justification for §2.1 and §5 and for not spending effort on the encode/decode ends.

Encoder parallelism is `--encoder-parallel auto`, and the log says what auto decided:
*"Proposed encoder parallel folding (mode=world) for ServerArgs (tp=4 sp=2 cfg=1 replica=8); the
loader keeps it for encoders wide enough to benefit"* — i.e. the 8-way world is folded into 8
**replicas** for the encoders, so each rank encodes the same text and the same reference image
redundantly. That is the right call at these sizes: sharding 0.07 s of text encoding across 4 ranks
would cost more in collectives than it saves. It is also why the reference image being large is
almost free in *time* (0.556 s) while being the thing that decides whether ref2va fits in memory.

The video VAE decode is **not** sharded either — 3.2 s, and identical to three decimal places across
the fp8, sage and NVFP4 arms, which is what a replicated stage looks like. It is 4 % of the request,
so there is nothing to win there; it matters only because it is the stage that ran out of memory in
the NVFP4 ref2va arm, being last in line behind the DiT's fp32 AdaLN.

## 4. Cache-DiT: three switches, and only the audited one is refused

There are **three** ways to ask for Cache-DiT, and the earlier version of this section conflated
them into "unavailable". They have to be kept apart:

```
MiniMaxH3DenoisingStage._cache_dit_requested()   # (a) quality == "high"          -> AUDITED preset, refused here
                                                 # (b) SGLANG_CACHE_DIT_ENABLED   -> generic knobs, OPEN
_maybe_enable_cache_dit()                        # (c) enable_cache_dit + cache_dit_params per request
                                                 #     enable_cache_dit=false is a kill switch and wins over (a)
```

`--cache-dit-config` is none of them: its own help string reads *"Enables cache-dit for **diffusers**
backend"*, and H3 runs the native pipeline (§2). That is the whole explanation for the byte-identical
measurement below — the flag never turned anything on.

`quality="high"` selects an **audited** preset rather than knobs an operator guessed:

```
minimax_h3/constants.py:64
  MINIMAX_H3_HIGH_QUALITY_CACHE_DIT_CONFIG: tuple[int, float, int] = (4, 0.04, 1)
  # Audited 4xH200 T2VA Cache-DiT parameters for quality="high" ...
  # Measured SSIM 0.931 / PSNR 28.16 dB against quality="lossless"
```

i.e. `max_warmup_steps=4`, `residual_diff_threshold=0.04`, `max_continuous_cached_steps=1`,
`Fn_compute_blocks=1`, `Bn_compute_blocks=0`, `enable_taylorseer=False`. **Send it top-level in the
JSON body**, not inside a nested object and not as a server flag:

```json
{"prompt": "...", "task": "t2va", "quality": "high", "num_inference_steps": 25}
```

It works there because `quality` is read via `request_extra_value()` (`openai/utils.py:121`, called
from `video_api.py:305`), which looks at `request.model_extra` and then at the containers
`extra_body` / `extra_json` / `extra_args` / `extra_params`; `VideoGenerationsRequest`
(`protocol.py:111`) is `ConfigDict(extra="allow")` and does **not** declare `quality`, so a top-level
key lands in `model_extra`. (`protocol.py:97`'s `quality: str = "standard"` belongs to
`VideoResponse`, not the request — do not read that as the default.) `cache_dit` 1.3.0 is in the
image. `scripts/sglang_case.py` plumbs it as `quality=high` / `QUALITY=high`.

**And on g7 it is refused.** All three arms — t2va fp8, ref2va fp8, ref2va bf16+LoRA — came back with
the same rejection:

```
MiniMax-H3 quality="high" is validated only for the strict 4xH200 fl2va deployment; mismatches:
  {'model_variant': {'expected': 'fl2va', 'actual': 'ref2va'},
   'num_gpus':      {'expected': 4,  'actual': 8},
   'quantization':  {'expected': None, 'actual': 'fp8'},
   'sp_degree':     {'expected': 4,  'actual': 2},
   'tp_size':       {'expected': 1,  'actual': 4},
   'ulysses_degree':{'expected': 4,  'actual': 2},
   'device':        {'expected': 'NVIDIA H200 (compute capability 9.0)',
                     'actual':   'NVIDIA RTX PRO 4500 Blackwell...'}}
```

The audit was run on **4×H200, fl2va, unquantized, TP=1 × U=4**, and the server enforces every one of
those six facts plus the device string. The `num_gpus: 4` and `device: H200` conditions alone make it
unreachable on an 8-card g7 no matter how the topology is arranged. That is a deliberate refusal, not a
bug: the vendor will only ship SSIM 0.931 where they measured SSIM 0.931.

**But only `quality="high"` is refused, and the refusal is explicitly scoped.** `constants.py` says so
next to the preset, in as many words:

> Process-wide `SGLANG_CACHE_DIT_*` environment controls remain available for manual experiments and
> are independent of this field.

So route (b)/(c) — `SGLANG_CACHE_DIT_ENABLED=1` at serve time, then `enable_cache_dit` and
`cache_dit_params` per request — is **open on g7**, with the same code underneath and the same knobs;
what it does not come with is the vendor's SSIM number. `_maybe_enable_cache_dit` gates the generic
mode on `generic_requested = generic_enabled and "quality" not in explicit_fields`, i.e. a request
gets knobs **or** the audited preset, never both — which is also why there is no combined arm here.
`server_args.py:3766` adds one caveat worth writing down: with `SGLANG_CACHE_DIT_ENABLED=true` and
both SP>1 and TP>1 it logs *"cache-dit is enabled with hybrid parallelism (SP + TP). Proceeding
anyway (SGLang integration may support this mode)"* — a warning, not a refusal, and our topology is
exactly that hybrid. Treat any TP=4 × U=2 Cache-DiT number as unvalidated by upstream.

**The version theory that used to be here was backwards.** It claimed our image predated the build
where g7e got Cache-DiT working on H3 (residual reading back as 0, so the cache never fires). The
dates are the other way round: g7e's `c0b6474` is **2026-08-17** and our `20518d85` is
**2026-09-18**, a month *newer*. Whatever fix that was, we already have it. And the theory was not
needed in the first place — the byte-identical result is fully explained by `--cache-dit-config`
being a diffusers-only flag.

What g7e measured, and what makes this worth an arm: **1.6× at 20 steps and 2.1–2.3× at 30 steps**
across four configurations, *better than simply cutting steps* at equal cost (6/6 cells, up to
+0.032 SSIM). Two of their operating notes transfer directly: the threshold has to be retuned per
resolution (480p `RDT=0.20`, **768p `RDT=0.16`** — note the env default is 0.24 and the audited H3
preset is 0.04, so the useful range spans 6×), and Cache-DiT is the **only** accelerator here that
does not dilute the multi-GPU gain, because it skips whole blocks and the all-to-all for those
blocks goes with them.

So "approximate schedule" is **open** on this image, as a third lever alongside §2.1 and §3.2 — see
§4.1 for what it actually costs in quality here. `scripts/cachedit.sh` drives it.

## 5. The real lever is the step count, and it needs three flags together

25 → 8 steps is **3.1×**, and it is not quality-free unless the weights were distilled for the short
schedule — which is what lightx2v's Turbo LoRA is. Two things [`REF2VA.md`](REF2VA.md) already
established and this arm depends on:

* **Pass no `--lora-alpha`.** The alpha is in the safetensors metadata (0.0625 for ref2v v1.0). The
  `--lora-alpha 128` in lightx2v's README is for a different file and is a 16× overdrive — it is the
  actual cause of the "melting" a previous customer reported.
* **bf16, not fp8.** `--lora-path` on a quantized layer falls back to dynamic LoRA and the dynamic
  wrapper is not quantization-aware: warmup dies on `'RowParallelLinearWithLoRA' object has no
  attribute 'quant_method'`. bf16 merges the adapter at load and costs nothing per step.

bf16 raises the DiT to 61.73 GB, i.e. 15.4 GB per card at TP=4 — which is why the third flag is not
optional. `r_lora8` (bf16 + LoRA + encoder offload) **loads fine and then OOMs in the warmup
forward**: 15.4 GB of weights leaves too little for ~15 GB of activations. `--minimax-h3-adaln-online`
takes 24.29/4 = 6.1 GB per card out of the resident weights, and the same arm runs at **63.26 s**.
The adapter targets attn/mlp projections, not AdaLN, so the two do not interact.

TP=8 is the fallback shape for the same arm (7.7 GB/card of weights instead of 15.4) at TP=8's
step penalty: 74.93 s. Slower than the TP=4 arm, still 2.3× faster than 25-step fp8.

**The same recipe works on t2va, and nothing had tried it.** t2va is served from the **FL2VA weight
partition** (`MINIMAX_H3_TASK_PARTITIONS = {t2va: fl2va, fl2va: fl2va, ref2va: ref2va}`), so
`minimax_h3_fl2v_turbo_8step_v1.0_768p_bf16.safetensors` is the matching adapter for a t2va server —
not only for a first/last-keyframe one. Same three flags, and t2va goes **105.37 s → 39.42 s**
(4.93 s/step × 8). That is the single largest measured win on this machine, and it makes t2va cheaper
per clip than ref2va is per *step*.

**The quality gate passed, twice.** `r_base` (25-step fp8, exact) vs `r_lora8_adaln` (8-step LoRA) on
the raw prompt at 1.0 / 3.0 / 4.9 s: same framing, same stroke geometry, no melting, no ghosting; the
8-step strokes are slightly rougher at the chalk edges. And `rir25` (25-step fp8) vs `rir8` (8-step
LoRA) on the **IR** prompt: same shot progression, `the first mark` appearing in the first second, and the same closing
frame — teacher stepped back, `[on-screen text]` complete, turned to camera. At 63.7 s against 177.2 s that is
an easy trade to put in front of the customer.

**Neither arm gets the handwriting right, and that is not a step-count question.** Both show the same
stroke incoherence (`PROMPT_IR.md` §3.4) — ink appearing away from the chalk tip, ink disappearing
between frames, intermediate glyphs that are not prefixes of the target. It is a latent-resolution limit
(a chalk stroke is ~0.5 of one 16× latent cell), so it is invariant to steps, precision and topology.
Do not read the 8-step arm's pass on framing and identity as a pass on written text.

**The IR prompt is free in the fast config too**: `rir8` (3337-character prompt) is 63.74 s against
`r_lora8_adaln`'s 63.26 s on a 126-character one. Prompt length is not a latency knob at any step count.

## 6. Two things this box is *not* good for, stated plainly

* **fp8 at TP < 4 is impossible** with the published bf16 checkpoint, so there is no configuration in
  which fewer than four of these cards serve H3 at fp8. A 2-card deployment has to be bf16 +
  adaln-online + all three CPU offloads, and even that OOMs in the warmup forward (§3.1).
* **A single p5.4xlarge H100 measured 127 s (t2va) / 213 s (ref2va)** — but layerwise-offloaded and
  therefore PCIe-bound, so it is not a latency reference for one H100, and the g7 numbers should not be
  read as "8 g7 cards ≈ 1 H100". They are a measurement of this deployment, not of the silicon.

## 7. Operating notes

* The readiness line is **`"The server is fired up and ready to roll!"`** (`server_warmup.py:389`),
  not "Uvicorn running": `http_server.py` runs warmup in `_run_server_warmup_after_http_live`, i.e.
  after the socket opens and after `GET /liveness` answers 200. A client that fires on "Uvicorn
  running" hits a mid-warmup server.
* `_degrade_after_oom` is **broken** in this build (`ValueError: field num_frames is declared with
  init=False`), so a warmup OOM aborts startup instead of retrying smaller. Watch for it explicitly.
* Frames must be **≡ 1 mod 8** and duration ∈ **[4, 15] s**: 5 s is 121 f (5.04 s), 10 s is 241 f,
  15 s is 345 f.
* Server start is **70–90 s** with weights on the node's NVMe.
* Renders must be written to the hostPath mount (`/data/...`), not the pod's writable layer — kubelet
  evicts the pod for exceeding `ephemeral-storage`.
* `kubectl exec` with a backgrounded process holds the stream open. Launch with
  `setsid nohup … > file 2>&1 < /dev/null &` and poll with separate short `exec` calls.
